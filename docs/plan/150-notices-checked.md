# Step 150 — The third-party notices checked against their sources

**Status: in progress** on `step/150-notices-checked`, red tests approved
by Volker on 2026-11-08 — commissioned 2026-11-07 (Volker) from Step 149's retrospective (LEARNINGS §5.82): after
Step 148, before the v0.2.1 release. The repository is being made known
widely now, and its attribution files are to be held by a check, not by
one comparison by hand, before that.

**Phase 1, measured 2026-11-08:**

- **The graph (scope 1): route (a).** `cargo tree --offline --locked`
  through `env!("CARGO")` takes 0.6 s and runs inside `cargo test`, as
  `step_90_sqlite3mc_engine`'s `cargo metadata --offline` does. It needs
  every package in the local registry: with a fresh `CARGO_HOME` fetched for
  the host only it fails, after a plain `cargo fetch --locked` it passes.
  CI's `check` job runs that fetch already, for Step 90's pin.
- **The markers (scope 3):** they read normal edges, per target: in the
  wasm32 graph of `kupferdraht-core` and a native one means unmarked, in only
  one of them the matching marker. A crate in neither is a build tool or
  behind a `cfg` no build sets: in no artifact, so no graph contradicts its
  marker. The CLI is no browser artifact, so the wasm32 graph is the library's.
  Twelve native targets: desktop, Android, iOS. The first plan counted build
  dependencies too, and CI refuted it: `cargo tree --target` resolves a build
  dependency for the host, so `errno` and `linux-raw-sys` changed sides between
  a Mac and Linux. `chacha20`'s wrong marker went with the lockfile update of
  PR #46.
- **One graph (scope 6): `cargo about generate about.hbs -m
  kupferdraht-cli/Cargo.toml -c about.toml`.** The report then lists 442
  versions, the notices' 445 without the two unpublished sqlite-remote crates
  (the hand-kept block) and `zerocopy-derive`. That one was the open question
  of Problem 3: zerocopy names it as a `cfg(any())` dependency, which holds
  its version in the lockfile and which no target compiles. `cargo tree
  --target all` lists it, cargo-about evaluates the `cfg`.
- **The CI job (scope 5):** a workflow of its own, `licenses.yml`, on `push`
  to `main` and on a pull request changing `Cargo.lock`, `about.hbs`,
  `about.toml` or the report. It gets cargo-about as the `audit` job gets
  cargo-deny, `cargo install --locked`, at the pinned 0.9.2 with `--features
  cli`: without the feature the crate installs no binary, and cargo still
  reports success. The release procedure does not regenerate.

**From the first Dependabot run (LEARNINGS §5.83):** `unicode-normalization`
0.1.26 added `Unicode-3.0` to its license, which only the section check
(scope 2) catches. A choice of licenses is stated in every section that has
one; the dual-licensed section, the largest, did not state it, and the

## Problem

1. **Two attribution files follow the dependency graph by hand.**
   `THIRD-PARTY-NOTICES` names 444 crate versions (377 crates) of
   `cargo tree -p kupferdraht-core -p kupferdraht-cli --target all -e
   normal,build`, grouped by license, with a target marker where a crate
   is pulled by the browser or the native builds only. It also names
   components outside the crate graph — SQLite3 Multiple Ciphers and the
   SQLite it embeds (`vendor/sqlite3mc/PROVENANCE.txt`),
   sqlite-remote-vfs / sqlite-remote-protocol (a git dependency in
   `Cargo.lock`), protoc, the Gradle wrapper — and the Kotlin bindings'
   Maven components with the versions `bindings/*/build.gradle.kts`
   declares. `docs/THIRD_PARTY_LICENSES.html` is generated by cargo-about
   from `about.hbs` and `about.toml`; the template keeps a hand-written
   block for the engine and the sqlite-remote crates, which cargo-about
   leaves out (vendored, `publish = false`).
2. **Nothing checks either file.** Step 140 (merged 2026-11-04) moved
   sqlite-remote-vfs to 0.6.0; three places kept 0.5.0 until Step 149's
   archive chore — the notices' crate list, their paragraph on
   components outside the graph, and `about.hbs`'s block. No release
   carried it (`git tag --contains` the Step 140 commits lists none);
   v0.2.1 would have. Every `cargo update` needs the notices edited by
   hand (Step 149: 16 packages moved, one added) and the HTML
   regenerated, and the gate passes on neither. `cargo deny` checks the
   licenses against the allow-list and the compliance workflow's ORT job
   analyses them for an SBOM; neither reads the two files.
3. **The two files cover different graphs.** Measured 2026-11-07: the
   HTML lists 454 crate versions, the notices 444. The HTML has 13 more —
   the dependencies of the third workspace member,
   `kupferdraht-uniffi-bindgen` (askama, goblin, uniffi_bindgen, …),
   which ships in no artifact — and lacks `zerocopy-derive` 0.8.48, a
   proc-macro the notices list (native targets only); why cargo-about
   does not see it is not known yet. The notices' header says the HTML is
   generated "from the same graph".

## Scope

1. **Crate list ↔ build graph, in the five-command gate.** A test reads
   the notices' license sections and compares the set of
   `name version` pairs with the graph, both ways: a missing, extra or
   stale entry fails, naming the crate, the version and the side that
   lacks it. Build metadata is part of the version (`wasi
   0.11.1+wasi-snapshot-preview1`). Where the graph comes from — phase 1:
   (a) the test runs `cargo tree --offline --locked` through `$CARGO`;
   (b) a committed snapshot of the graph, which the test checks against
   the notices and a CI step against `cargo tree`. Recommendation: (a),
   one source and no extra file, if phase 1 confirms it runs inside
   `cargo test` here and on CI.
2. **The license section.** Each crate stands in the section its
   `license` from `cargo metadata` belongs to; a section that picks one
   license from a choice says so. Recommendation: in, same test.
3. **The target markers.** "(browser target only)" means in the wasm32
   graph and in no native one; "(native targets only)" means in no wasm32
   graph. It needs the list of native targets — phase 1 takes it from the
   targets the bindings are built for, or the markers stay unchecked.
4. **The components outside the graph.** SQLite3MC and SQLite against
   `PROVENANCE.txt`, the sqlite-remote crates against `Cargo.lock`, in the
   notices and in `about.hbs`'s block alike, and the embedded licenses
   `PROVENANCE.txt` records in both. The Kotlin section against
   the Gradle files' literal versions (jna, kotlinx-coroutines,
   kotlin-stdlib, the gobley plugins). Recommendation: all of it — the
   same drift, the same kind of test.
5. **The HTML report in CI.** A job regenerates it with cargo-about at a
   pinned version (0.9.2 today) and fails on a diff, on `push` to `main`
   and on a pull request that changes `Cargo.lock`, `about.hbs` or
   `about.toml`. Phase 1: how the job gets cargo-about (`cargo install
   --locked` or a prebuilt binary) and whether the release procedure
   regenerates instead.
6. **One graph for both files** — phase 1. Either the HTML leaves out
   `kupferdraht-uniffi-bindgen`'s dependencies (cargo-about's workspace
   selection or `about.toml`) and gains `zerocopy-derive`, or the
   notices say which graph each file covers. Recommendation: one graph,
   the notices'.
7. **The notices' header** drops "on 2026-11-02": with the test, the date
   says nothing about how current the list is.
8. **Docs:** README's "Building" section (how the notices are updated,
   what checks them), the release procedure in `CHANGELOG.md` if 5. lands
   there, CHANGELOG `[Unreleased]` → Fixed if 6. changes the HTML's
   content. CLAUDE.md is untouched: the test is part of the five.

## Out of scope

- Generating `THIRD-PARTY-NOTICES` (a second cargo-about template, say):
  the target markers, the "used here under" choices and the components
  outside the graph are not in cargo-about's data. A check keeps the
  hand-written file honest without replacing it.
- The license texts themselves, and whether a license is acceptable
  (`cargo deny`, ADR-0016).
- The Swift package (no package dependencies today) and the browser
  bundle's npm side (none).
