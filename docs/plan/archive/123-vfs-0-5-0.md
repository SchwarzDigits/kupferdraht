## Problem

sqlite-remote-vfs 0.5.0 (tag `v0.5.0`, `2c6930f`) changes no interface and
makes the server storage more robust:

- the storage server retries a request on a fresh connection when its
  connection to PostgreSQL broke;
- when the server still answers a commit with an internal error, the crate
  sends the same commit again instead of failing the database for good
  (`Failure::Rejected`); after `reconnect_timeout` the database is
  `Failure::Unreachable`, which heals.

Kupferdraht pins `01688f2` (0.4.0). A commit failed by the server so far ended
the database's use until a reload; the natrium web SDK's tester saw an open
fail with `disk I/O error` from the storage server once (its gap list,
entry 4) — not diagnosed, possibly this class.

## Design

- **D1 — pin `rev = "2c6930f"`** (v0.5.0) instead of `01688f2`; the
  lockfile changes only the crates of that repository.
- **D2 — no code change.** Kupferdraht already maps `Failure::Unreachable` to
  `ServiceUnavailable` while the storage heals (Step 113,
  `storage::browser::check_database`); `Rejected` stays a storage error.

|---|---|

| resume | `POST /v14/access` 200, `OPEN-OK` |

**One unexplained failure, not reproduced:** the first run's resume met
`POST /v14/access` 403 (`SessionExpired`) about ten seconds after its
login; a second run with a fresh profile passed end to end. The refresh
cookie lives in the session row on the storage server and is written
again after the login's rebind; the smoke stops the browser two seconds
after `LOGIN-OK`. A lost commit of that row would explain the 403, as
would a cookie revoked by the backend — not determined. The storage
side ruled the first out: the crate acknowledges a commit only after the
server's `CommitAck` (after PostgreSQL's commit), also on 0.5.0's resend
path. Noted in `open.md` §75 — closed by Step 124: the smoke stopped
Chrome before it wrote the rotated refresh cookie to disk.
